# Literature synthesis checked through October 20, 2026

This targeted supplement connects ten studies already in the living bibliography. It is not an exhaustive new census, a new manuscript release, or a dataset expansion. Some studies were first released before October 1: newly collected does not mean newly published. Mechanisms below follow the inspected primary-source versions; results have not been independently reproduced here.

## 1. What changes: the task harness or the improvement procedure?

**Harness²** distinguishes task-local Propose–Probe–Compose exploration from a persistent improvement library. Each new task starts from a common execution harness; retained components and refinement lessons inform later improvement. Fixed stage instructions, model weights and decision rules must not be described as evolved. **RSIFlow** retains workflow-selection skills and principles while coordinating changes to model parameters, harnesses and task artifacts. Its complete gain cannot be attributed exclusively to a harness or meta-harness. **Harmony Harness** separates security and functionality objectives and organizes general versus environment-specific edits; its optimizer and factorization are supplied designs, not discoveries.

**Comparison implication:** task gains, retained improvement guidance and improved subsequent optimization are distinct claims. A label such as “general” does not establish transfer of every component.

## 2. What did an edit repair—and what did it break?

**Does Failure Feedback Direct Agent Self-Modification?** separates target repair, spread, collateral breakage and net score change. A winning lineage does not prove that its individual edits repaired the diagnosed failures; lack of target-specific advantage does not show that feedback is always useless. **GSO** retains a metaskill for constructing new task-specific skills, rather than reusing task particulars, and checks candidate changes through validation executions. **Harness Evolution Hits a Ceiling** crosses seed/evolved harnesses with base/trained models to distinguish runtime dependence from parametric carryover. Its benchmark-dependent limits are not a universal ceiling.

**Reporting implication:** distinguish proposal, evaluation, retention, activation and outcome. Preserve rejected candidates and regressions when reported, alongside viability exclusions and the original evaluation setting. We cannot recover unreported failures or claim an unbiased population-level failure rate from published survivors. Missing or unreviewed evidence is not a negative result.

## 3. Memory content, memory procedures and trained policies are different objects

**MemSkill** revises reusable memory-construction instructions alongside controller learning; its fixed designer/executor and seed operations are not themselves evolved. **ERSkill** evolves retrieval programs built from supplied primitives and trains a router; capability and deployment frontiers distinguish oracle usefulness from routed performance. A generated skill is not necessarily retained or used. **SESA** combines external solver skills with policy self-play, including utility-based eviction. Its full training gain cannot be assigned to the external memory bank alone.

**Comparison implication:** storing new experiences, changing how memory is built or retrieved, and training the model/controller must be recorded separately. These systems are not uniformly weight-free.

## 4. A definition is not an additional benchmark result

**Self-Evolving Agent Harness** (`self_evolving_agent_harness2026`), [2610.18813v1, Sections 2–3](https://arxiv.org/html/2610.18813v1), distinguishes feedback-driven revisions that persist across runs from unchanged logging or context compaction. We use this as conceptual background, not evidence of another successful intervention or achieved general RSI.
